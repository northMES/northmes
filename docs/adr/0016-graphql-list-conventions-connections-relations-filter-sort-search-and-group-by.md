# GraphQL list conventions: connections, relations, filter, sort, search and group by

## Context and problem statement

Every module and plugin adds lists to the supergraph: production orders, operations, job orders, customers, articles, the core registers, the audit list and the connector import log in release 1, and many more later. Krister Johansson decided that every GraphQL list is a Relay connection with edges, node and pageInfo; that relations resolve on the server as objects, so a production order carries its customer and the client sends no second query; and that every list offers filter, sort (one `orderBy` argument), search and group by.

Without one convention each list invents its own arguments, operators and paging, and agents hand-write the same inputs again. Federation ([ADR 0015][adr-0015]) adds two constraints: a list can filter and sort only on columns its own subgraph holds, and composition merges shared input types by intersection without an error. This ADR fixes the shape and semantics of every list field and the one declaration that generates them. It covers the list kit in `@northmes/sdk`, the declarations in each module's contracts package, and the web hooks in `@northmes/web-sdk`.

## Decision drivers

* The decided requirement: connections, relations as objects, filter, sort, search and group by on every list.
* Paging must stay fast under row-level security, deep into a list, with nullable sort keys.
* Hive demand control must price every list from its slicing arguments.
* Shared filter inputs must print identically in every subgraph.
* Plant-local days, weeks and production days must be filterable and groupable in the plant's zone ([ADR 0024][adr-0024]).
* Metric values are stored in SI and converted on the server ([ADR 0023][adr-0023]).
* One declaration per list, so a coding agent writes data, not resolvers and SQL.

## Considered options

* Offset paging (`limit`, `offset`) with plain arrays and arguments chosen per list.
* Relay connections with hand-written filter inputs per list, as in the earlier attempt.
* A schema generator such as PostGraphile with its connection-filter and aggregates plugins.
* Relay connections with keyset cursors, generated by an SDK list kit from one declaration per list.

## Decision outcome

Chosen option: "Relay connections with keyset cursors, generated by an SDK list kit from one declaration per list", because it meets the decided requirement within NestJS code-first, it pages in constant time under row-level security, and it gives agents one place to change.

Root list field and connection:

```graphql
<module><Entities>(first: Int = 25, after: String, last: Int, before: String,
  filter: <T>Filter, orderBy: [<T>OrderBy!], search: String,
  includeArchived: Boolean = false   # archivable entities only
): <T>Connection!

type <T>Connection { edges: [<T>Edge!]!  pageInfo: PageInfo!  totalCount: Int!
  aggregates: <T>Aggregates!
  groupedAggregates(groupBy: [<T>GroupBy!]!, having: <T>Having,
    orderBy: [<T>GroupOrderBy!], first: Int = 100): [<T>Group!]! }
type <T>Edge { cursor: String!  node: <T>! }
```

| Item | Rule |
|---|---|
| Page size | `first` defaults to 25 in the schema, range 1 to 100; `first: 0` is refused |
| Direction | `last` or `before` selects backward paging and `first` is then ignored; `after` with `before` is refused |
| Cursor | opaque `base64url(JSON [1, orderSignature, sortValues..., id])`; sort values are Postgres text; a cursor from another `orderBy` is refused with `core.list.invalid_cursor` |
| `pageInfo` | per the Relay specification; `hasNextPage` exact when paging forward; `hasPreviousPage` is `after != null` when paging forward; mirrored backward |
| `orderBy` | `{ field: <T>SortField!, direction: SortDirection = ASC, nulls: NullsOrder }`, at most 3 entries, no repeated field, nulls LAST by default in both directions, `id` appended as tie-breaker; a nullable first key is split into its non-null and null partitions |
| `filter` | one typed operator input per declared field (`eq`, `ne`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `between`, `contains`, `startsWith`, `isNull` by type) plus `and`, `or`, `not` |
| Null semantics | positive operators never match NULL; `ne`, `notIn` and `not` include NULL rows; `in` and `notIn` take at most 1 000 values |
| Plant time | an instant declared `plantDate` also gets `<field>Date` and `<field>ProductionDay` (`DateFilter` in the plant zone) |
| `search` | trimmed, at most 100 characters, case-insensitive substring over the declared search fields and reference searches |
| `totalCount` | one `count(*)` with the same filter, only when selected; append-only lists (audit list, event log, import log) declare `totalCount: false` |
| Aggregates | `count`, `sum`, `avg`, `min`, `max` over every row the filter and row-level security let through, ignoring paging |
| Group by | 1 to 3 keys from `<T>GroupBy` (fields, plant-time buckets `DAY`, `WEEK`, `MONTH`, `PRODUCTION_DAY`, references); typed `keys`; at most 500 groups; `having` on `count` and `sum` |
| Errors | `BAD_USER_INPUT` with `core.list.bad_argument`, `core.list.invalid_cursor` or `core.list.ref_search_too_broad` |

Relations:

* To-one inside a module: an object field batched through a request DataLoader.
* To-many inside a module: a nested connection `(first: Int = 25, filter, orderBy)` without cursors, with `totalCount` and `aggregates` per parent, one windowed statement per relation level. Paging past the first nested page goes to the root list with a parent filter. Filters on to-many relations use `some` and `none`.
* To another module: a nullable object field returning a Federation reference `{ __typename, id }`. Only the foreign key is filterable (`<ref>Id: IdFilter`); a declared `<ref>Search` runs a two-step lookup through the owner's API module and refuses more than 1 000 matches.
* The owner throws a typed `NOT_FOUND` for a hidden or unknown referenced row instead of returning null.
* A list cannot sort by another module's field. A screen that needs it gets a read-model column through an event, reviewed like any copied column. A field a plugin contributes to another module's entity is not filterable, sortable or groupable in the owner's list.

One declaration generates the rest. `defineList` in the module's MIT contracts package declares fields with their filter, sort, search, group and aggregate flags, references, nested lists and the default order. `listKit` in `@northmes/sdk` generates every input and output type, the `<T>ConnectionResolver` (which carries the list's permission guard), the SQL, the cursor codec and the nested loaders. The SDK adds the plant predicate `scope_id = $activePlant` next to row-level security, and every list's default order gets an index `(scope_id, <sort columns>, id)`. Every connection field carries `@listSize`, and `requireOneSlicingArgument` is false. On the web, `useListState`, `useConnection` and `DataTable` read the same declaration. The master-data kit's list block is this declaration ([ADR 0022][adr-0022]).

### Consequences

* Good, because measured batching is large (internal research note 34): 100 orders with their customers ran in 3 SQL statements at p50 8.4 ms through the gateway, against 87 statements and 16.7 ms without batching.
* Good, because keyset paging stays fast deep into a list: with 50 000 orders in one plant, `OFFSET 42500 LIMIT 101` took 14.1 ms in `EXPLAIN ANALYZE` against 0.06 to 0.11 ms for the keyset predicates, and a page at 85 percent depth took 4.19 ms through GraphQL with the null split against 17.45 ms with one OR query.
* Good, because the drift rule of [ADR 0015][adr-0015] stops an old plugin from removing an operator from every list.
* Good, because group by gives screens filter chips with counts and load per machine per production day in the same request as the page.
* Bad, because lists make no snapshot promise: a row whose sort value moves across the cursor between pages may be skipped or read twice. Screens refetch the visible page when an event names a listed id.
* Bad, because `ILIKE` search cannot use a trigram index under row-level security (33.7 ms at p50 with 50 000 orders); plant lists in release 1 hold hundreds to a few thousand rows, so this is accepted.
* Bad, because a hidden related row returns `customer: null` plus one error for that row; screens wrap relations the user may lack permission for in `@include`.
* Bad, because the schema default `first: Int = 25` means a call with only `last` also receives `first`, which the convention resolves by ignoring `first` on backward paging.
* Neutral, because internal research note 34 estimated 17.5 to 24 developer days gross for the server kit, gateway limits and web hooks, partly overlapping work already budgeted for the shared packages.

### Confirmation

* `lists/*.int.test.ts` against Testcontainers Postgres: seven `orderBy` cases walk all rows forward and backward and match Postgres's own `ORDER BY`; a deleted cursor row; a cursor from another `orderBy` refused; every operator against hand-written SQL including NULL semantics; `deadlineAtDate: { eq: "2026-10-26" }` across the Europe/Stockholm DST change; `some` and `none`; a reference search over 1 000 ids refused; a hidden customer returns typed `NOT_FOUND`; 100 orders with customers in 3 statements; group limits refused above 3 keys and 500 groups.
* List kit unit tests: connection fields resolve through generated `@ResolveField` methods; generated resolver methods carry `design:paramtypes`; input classes exist before the type thunk runs.
* `gateway/composition.test.ts`: `NORTHMES_SDK_TYPE_DRIFT` fails when two subgraphs print `StringFilter` differently.
* `gateway/guards.int.test.ts`: 100 orders with 100 operations each is refused by cost; a call with only `last` is accepted.
* `schema/list-conventions.test.ts` (proposed name): walks `schema/api.graphql` and fails on a root field that returns a plain list instead of a `<T>Connection`, with an explicit allowlist that starts with the planning board's range query.
* Web: a `useListState` URL round trip test, and a `DataTable` test that sortable headers come from `<T>SortField` and set `aria-sort`.

## Pros and cons of the options

### Offset paging with plain arrays

* Good, because it is the simplest to build and to call.
* Bad, because it fails the decided connection shape.
* Bad, because deep pages scan and discard rows; rows inserted between pages shift every later page.

### Relay connections with hand-written filter inputs per list

* Good, because each list can fit its screen exactly.
* Bad, because every list repeats the same inputs, SQL and cursor code; the earlier attempt mapped its filters to Prisma shapes that Kysely does not have.
* Bad, because operators and null handling drift between lists.

### A schema generator such as PostGraphile

* Good, because filters and aggregates come ready, and its operator and aggregate names are prior art NorthMES follows.
* Bad, because it replaces NestJS code-first resolvers, which the project decided, and its own README warns that default filters make it easy to overload the database.

### Keyset connections from one declaration through a list kit

* Good, because one declaration drives types, SQL, cursors and the web table.
* Good, because it was prototyped against Postgres under row-level security with the in-process gateway, including the traps it found and their fixes.
* Bad, because the kit is a large shared component that must be built before the first list ships.
