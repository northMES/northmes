Recommendation: A, tabs and edit mode, with B's move buttons as Widget actions items and C's Add widget tile in edit mode

A keeps what the request asks for in view: tabs that are visible and one activation apart, the full 12-column grid at 1280 and 1440, and an edit mode that keeps everyday use free of controls and saves a session as one command, which also limits audit rows and lets Cancel undo a session. Two parts of the other options are stronger and fit into A without changing its model. B's Move up, down, left and right buttons move a widget with no keyboard mode to learn; in A they become four items in Widget actions, a second path without dragging beside the move button. They stay out of A's settings Sheet: its overlay covers the grid and the widget changes only on Apply, so a move there would show nothing and could put the widget under the Sheet. Chosen from the menu, a move happens in plain view: the grid scrolls the widget into view and the polite region names the new column and row. C's tile shows where a new widget lands; inside A's edit mode it takes the place of Add widget in the edit bar, so adding takes two steps once the tab is in edit mode. B's side column halves the grid to 6 columns at 1280 and 1440, and C hides the tabs behind a menu, against the request for a tabs system, and its settings do not fit a Small widget. The cost of A is the keyboard move layer on react-grid-layout (frame G) and a version check for two people editing one shared tab (question 16).
