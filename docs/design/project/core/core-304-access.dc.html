Access management and the no-access states

Roles, assignments, a user's access, the users list and form, and the no-access states of core inside the D2 shell at Plant A, for the plant admin and the company admin. Rows 1 to 4 below hold the frames; each frame names its theme and size, and the chip of each screen frame names its route.

Issue
#304, core: Design access management and the no-access states, plan id E05-S06-T01
Story
E05-S06 (#54), grant roles per plant and check permissions at the row's scope. The UI tasks that wait on this page: the role and assignment screens of E05-S06 (#54), the user pages of E05-S08 (#56), and the forbidden and access-lost states the shell and screenRoute show (E04-S02 #40, E04-S07 #45).

Assumptions

  • Every value is fictional: Acme AB, its plants, the people, usernames, roles, permission ids marked invented, correlation ids and dates. The implementer takes layout, region order, states, copy, the keyboard model and slot placements, not demo numbers.
  • The plain line of each permission is proposed, because the manifest declares permissions without a label (question 4). The ids core.user:read, :create, :block, :resetPassword, core.role:read and core.roleAssignment:manage are proposed (question 3); acme.toolLife:read, acme.toolChange:record and kanban.board:read are invented for the page.
  • Plant admin and IT are custom roles of Acme AB, because core ships no plant admin role (question 6). Plant admin holds Viewer's two read permissions, so Shift lead needs three permissions Jonas Holm lacks at Plant A.
  • From Plant A the pages read assignments at Acme AB and at Plant A, never at Plant B (question 1). Holder counts, a user's roles and every refusal name only those two places.
  • The D2 admin preset draws every Administration entry. A narrower Plant admin role would show fewer, such as no Audit log without core.audit:read (NO3).
  • States the shell owns stay D2's. NO7 and NO8 redraw ST29 and ST30 unchanged for a plant without a role, because pages in shell/ cannot be mounted from core/. The access-lost dialog takes the 480 px box of D2's reload dialog, so the two shell alertdialogs match.
  • A role change and an assignment apply from the holder's next action. The role editor names the holders at Acme AB and Plant A, and the remove dialog names what another role still allows.
  • Every color is a D1 token. NO26 lists the values that are not tokens; each is a question for the implementer.
  • The users list takes loading, empty, error and forbidden from the canonical list page unchanged, with users as the noun, so row 3 draws no frame for them.

Proposals that need Krister's yes

Row 1, roles

  • The roles list is one DataTable with two fixed group rows, custom roles of Acme AB first, then default roles from modules, with the columns Defined by, Permissions, Held at Acme AB and Plant A and Last changed, and the canonical grouped pager "2 groups, 11 roles". The list at 320 keeps the groups and counts and folds Defined by into Filters (RO1, NO11).
  • Row menus: Edit role and New role from the role on a custom role, only New role from the role on a default role, and none on Company admin (RO35, RO37, question 34).
  • Start from offers No role first and as the default, then every default and custom role (RO11). The copy is one-time: "The new role copies its permissions once. It does not follow later changes to Planner." (RO13)
  • New role and the role editor share option A's two columns: the fields and the checklist on the left; the holders, the changes, the reason and the buttons on the right. Option C put Create role in a sticky footer (RO11 to RO20).
  • Without core.role:manage the list has no New role and no row menus, a role has no Edit role, and a note names the permission (RO27 to RO30). The edit route opened by URL reads "No access to Edit role" (RO31, RO32).
  • A default role offers the page action "New role from Planning admin" (question 32), and the Holders tab shows to every reader (question 33) (RO25, RO29).
  • After Save role the role detail replaces the form with focus on its h1 and the note "Shift lead saved. It applies to 2 people from their next action." (RO41). A Save refused for the whole role shows the error summary "Shift lead was not saved" with the missing permission at Acme AB and keeps every change (RO39).
  • A read-only role lists only the permissions it includes, by module, each with a check icon, and keeps Not installed marked (RO29).

Row 2, assignments and a user's access

  • Where comes before Role in Add role, and the listbox keeps a role the assigner cannot give, locked, with up to three of its missing permissions and their ids (AS3).
  • A plant admin reads "A company admin of Acme AB can remove it." in place of Remove on a company assignment (AS1).
  • A refusal from the server lands in the error summary, which takes focus and links to Role; the place, the role and the reason stay (AS5).
  • The Add role form keeps its main column at 760 px, the width of the canonical form, also at 1920 (AS16).
  • The role picker lists custom roles, then default roles, each by name, as the roles list does. A role the person already holds says so first, then still names what the assigner lacks (AS3).
  • The Access tab keeps the card headings and Add role in its loading and empty states; a failed roles load leaves out What the person can do, which is computed from the same roles (AS19 to AS24).

Row 3, users

  • New user is drawn for Karin Dahl, because in the page's data Plant admin lacks productionStart.report:create, so Jonas Holm could not give a new operator the Operator role (question 36).
  • The create form has no password field: NorthMES creates a temporary password and shows it once in a dialog, never in a toast (US5, US17).
  • The username refusal does not say whether the name is in use or retired, because "in use" could reveal a user of another company (US9).
  • The list shows no email and no last sign-in (question 13) and leaves out Lena Ek, who holds no role at Acme AB or Plant A (question 38). Jonas Holm's own row keeps its menu (question 39).
  • The reason stays optional on Block user, Unblock user and Reset password (question 9).

Row 4, no access, keyboard and focus

  • A page opened by URL without the permission has the title and h1 "No access to Roles", an EmptyState without a heading of its own that names the missing permission, and Go to Planning board as the way out (NO1).
  • The access-lost dialog is an alertdialog over the inert page; focus starts on Go to Plant A and Escape does nothing (NO9, NO25, NQ1).
  • After Remove role focus goes to the next row's role link, else to Add role (NO24, NQ2).
  • After Add role the user's page replaces the form, its h1 takes focus and one polite announcement follows (NO21).
  • When the reader may not read roles, the Role cells on the Access tab read No access as the Granted by cells do, Add role is left out and Remove is named by the place (NO5).
  • The access-lost dialog shows only Go to Plant A when one plant is left, and only Your plants when none is left (NO25 notes).
  • The announcement copy and the final English copy by region in NO26.

Known limits

  • AS25 and AS26 draw the effective permissions region denied with the copy of rule 14.10, which names core.user:read. A reader of a user's page already holds that permission, so the permission the region names waits on question 16.
  • AS9 and AS10 draw the first reading of the No access cells, every permission listed with No access where no role grants it; NO5 and NO6 draw the second, a reader who may not read roles. Question 29 picks one.
  • The Filters sheet of the roles list at 320 is not drawn. It holds Defined by, as the canonical Filters sheet of #222 holds the list's filters.

Open questions

From the variations round, with its numbers. Questions 17 to 21 are answered by the decision: 17 by the access-lost dialog, 18 by keeping ST29, 19 by the title "No access to Roles", 20 by option A's rule to hide an action and name who can, and 21 by Add role as its own route.

1
Row-level security on core.role_assignment: may the pages at Plant A read a user's assignments at Plant B? It decides holder counts, a user's full access and the text of a refused block.
2
Should users, roles and assignments also be reachable under /admin, which needs plant-free fields beyond the release 1 list of ADR 0066?
3
Permission ids for assigning roles, reading roles and reading, creating, blocking and resetting users. May a planner read role names?
4
Where do the plain-language label and description of each permission come from: a manifest field per permission, also shown in the generated permissions reference (E19-S03)?
5
Are module default roles read only? Does a role made from a default role keep a link to it, and does an upgrade that changes the default role show anywhere?
6
Does core ship a plant admin default role, and what does it hold?
7
Does the catalog record a level, company or plant, per permission, and should assigning a company-level permission at a plant warn that it has no effect there?
8
The refusal error: one code that lists every missing permission (proposed core.role_not_held with details.permissions), or core.forbidden with one permission?
9
Is a reason required to remove an assignment, change a role or block a user?
10
Removing the last company admin, or your own admin role: refuse, warn or allow, given northmes company add-admin as the way back?
11
Does creating a user take the first role and place in the same command, and where does can() check the create?
12
Can an admin add an existing user who works for another company, and how is that user found without showing other companies' users?
13
Does the user list show email, last sign-in or a pending temporary password, which core.user_directory does not expose?
14
Are unblock, rename and change of email in release 1? E05-S08 lists create, block and reset password.
15
Does the UI show the .invalid placeholder address or No email (M-08)?
16
Which read field returns another user's effective permissions at a plant?
22
Should any FORBIDDEN make the shell fetch the module list again, so the sidebar drops entries the user lost?

Which reading of B's No access cells holds: every permission listed with No access where no role grants it (AS9), or No access in the Granted by cells when the reader may not read roles (NO5)?
