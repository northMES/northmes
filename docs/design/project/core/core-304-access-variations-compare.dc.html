Recommendation: A, by person, with parts of B and C

A fits how the sources describe the work. An assignment is a (user, scope, role) row that an admin adds one at a time, so A puts Add role on the user's Access tab, with a picker that shows which roles the assigner can give at Plant A before anything is submitted; B shows the same refusal only on Save. A doomed submit then never reaches the server or the security log, and the server's refusal in the error summary stays the fallback for Acme AB, which a plant route cannot check. The grouped checklist keeps 36 permissions, and every plugin's additions, in one column at any width, and the list of what a user can do, with the role and place behind each permission, answers the support question without a matrix. B's matrices give the best overview of a plant and the fewest steps to give one person a role, but eleven roles already overflow 1440, one save becomes several commands, and screen reader users meet 185 checkboxes in a grid of 407 cells. C's role-first flow starts the common task from the role instead of the person and spreads a person's access over role pages. Keep from the others: C's "Start from" on New role (a one-time copy, question 5) and its Holders tab as a read-only list on the role detail; B's title "No access to Roles", which matches D2's unavailable module state, and its "No access" cells for denied relations; and C's dialog after close code 4403, which reuses the reload dialog's rules (inert page, one h1, saves refused) and settles Q22. For a plant without a role, keep ST29 as approved, so no message tells a user that some company has a plant at that path. For question 20, hide an action the reader cannot use on a record, as Sara Nyberg's page leaves out Block user and Reset password, and put a line naming who can in its place inside a list, as A3 does for Remove; keep a locked choice visible with its reason, as A2's picker does.
