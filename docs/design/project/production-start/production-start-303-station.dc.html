Operator station

The production-start station screen inside the D2 station frame: pairing a station, badge sign-in and Switch operator, the job list beside the selected job with Start, Pause and Finish, the report form with the docked keypad, the last reports, the report dialogs and corrections, a lost connection, idle sign-off and the page states. Rows 1 to 4 below hold the frames; each frame names its theme and size.

Assumptions

  • Every value is fictional: Acme AB, Plant A, Plant D, the people, the stations, the pairing code and address, and the job, article and machine numbers. The implementer takes layout, region order, states, copy, the keyboard model and slot placements, not demo numbers.
  • Now is Tue 3 Nov 2026 at 14:06 plant time; the frames after a code ran out, SI41, SI42, SI45 and SI46, are at 14:17. Report times are record times (proposal 21.25).
  • Press 4 is bound to one machine, so it shows no machine switch. Press cell 1 has Press 3 and Press 4 and shows the switch in the frame's header slot (JO22, JO30, JO31, RE22, RE23).
  • Finished jobs stay on the station for the production day under "Finished today" (question 21.2).
  • Overdue and planned on another machine show as words only: "Start overdue", "Planned on Press 3" (question 21.1).
  • Anna Berg typed 80 good on 5002.10 and changed job without sending, so 5002.10 carries the Unsent entries badge.
  • The start of a job is a row among the last five reports, with no Correct (question 21.5).
  • Anna Berg may correct the station's reports today, as the proposed operator rule says (question 21.6). The report has no note field (question 21.8).
  • Quantity fields are 56 px high, the sign-in fields, buttons and reason rows 48 px, keypad keys 72 px at 1920 and 64 px at 1280 and in portrait. No D1 token holds these sizes (question 21.9).
  • The D2 frame is frozen: the long-strings frame keeps its English top bar (question 21.33), and the parts set aria-busy on their own regions because the frame has no busy prop (question 21.32).
  • Five wrong PINs for one badge pause PIN sign-in for that badge for 5 minutes, as five unknown badges pause badge sign-in (question 21.35).
  • Every color is a D1 token.

Proposals that need Krister's yes

Row 1, pairing and sign-in

  • The pairing screen's top bar reads New station and Not paired, the h1 is "Pair this station", and a new code replaces an expired one by itself (SI1 to SI4).
  • The admin approves in a Dialog from the Pairing requests section of the Stations page. The Dialog shows the request's facts, including the address it came from, and a Select of the stations without a paired computer. Nothing is transcribed, and no Decline action is drawn (SI5, SI6).
  • After the approval the admin's focus moves to the station's name in the list, and the station shows a success Alert above the badge card until the first sign-in (SI7 to SI12).
  • While badge sign-in is paused, the Badge field keeps focus with aria-disabled, so a scan goes nowhere, and Sign in with username becomes the primary button (SI25 to SI28).
  • The PIN screen says "Badge read. Enter your PIN." and shows no name before the PIN is checked (SI17 to SI20).
  • At a plant in onboarding the station shows no sign-in form and says that sign-in opens there by itself (SI37 to SI40).
  • When a code runs out, the station shows a new one with a status line, and an approval that comes too late shows the error in the Dialog with Close only; the new request is in the list (SI41, SI42, SI45, SI46).
  • A wrong username or password keeps the username, clears the password and shows one error under the form; a wrong PIN clears the field and keeps focus there (SI48 to SI51).

Row 2, station home

  • "No job selected" with one line of guidance in the empty and error states (JO20 to JO24).

Row 3, lost connection, idle and focus

  • A session that ends on Send goes to the sign-in screen with a Report not sent notice, and the same operator's scan sends the kept report without a second press (OF6, OF7, OFQ5).
  • Another operator's scan signs that operator in, and the kept entries stay hidden on the station (OF8, OFQ2).

  • The error under Send stays after the connection is back, since it says to press Send again (OF5, OFQ4).

  • The automatic reload is drawn at the sign-in screen (OF14, OFQ3), and the notices use the Info icon on --info-subtle.

Row 4, reporting and corrections

Frame and routes

  • Sign-in is on /station/$stationId with the h1 "Sign in at Press 4". Switch operator has the h1 "Switch operator" and the document title "Switch operator · Press 4 · Plant A · NorthMES". The pairing screen's route is open (21.13).
  • The admin side is the core module's (modules/core/web) and mounts the D2 shell through production-start/Shell.dc.html with role="admin": Administration, Stations current, New station in the top bar, the release 1 top bar without the bell. Badge reader, PIN and keyboard model

  • The Badge field takes focus through a ref when the screen loads, never autofocus. The reader types the badge number into that field and ends with Enter. No global key listener reads badges anywhere.
  • After a scan that matched no badge the field is cleared and keeps focus, so the next scan lands in it. While badge sign-in is paused the field keeps focus with aria-disabled="true" and takes no input.
  • PIN: one input with type="password", inputmode="numeric" and autocomplete="current-password" that accepts paste and autofill, never one box per digit. On a station without a keyboard the docked keypad shows beside the card with System keyboard (aria-pressed="false"); on a station with a keyboard it starts hidden behind Keypad. Keys are buttons with tabindex="-1" that add to the field and keep focus there.
  • Username: type="text", autocomplete="username", autocapitalize="none", spellcheck="false". Password: type="password", autocomplete="current-password", paste allowed. The password needs letters, so this screen has no keypad. No CAPTCHA.
  • Five unknown badges within 60 s pause badge sign-in on the station for 5 minutes; the sixth attempt returns 429. Five wrong PINs for one badge pause PIN sign-in for that badge for 5 minutes (proposal, question 21.35).
  • A code is valid for 10 minutes. When it runs out the station asks for a new one and shows it by itself, with the "New code." line as role=status (SI41, SI42); the old request leaves the admin's list and the new one appears.

ARIA, names and announcements

  • Badge is labelled "Badge" and described by "Hold your badge to the reader."; after an unknown badge also by the error, with aria-invalid="true". While paused the field is described by the Alert.
  • The polite region says "Badge not recognized. Scan again or sign in with your user name", "Badge sign-in is paused until 14:08.", "Username or password not correct. Check both and sign in again." and "PIN not correct. Enter it again, or scan your badge again." once each.
  • After a wrong username or password, Password is cleared and described by the error under the form; neither field gets aria-invalid, since the server does not say which one is wrong. After a wrong PIN, PIN is cleared, gets aria-invalid="true" and is described by its hint and the error. While PIN sign-in is paused, PIN keeps focus with aria-disabled="true", described by the Alert.
  • The keypad is a group named by its caption "Keypad for PIN"; Clear is named "Clear PIN" and Delete "Delete last digit". The pairing code is named by "Pairing code"; the admin's steps are an ordered list named by its lead line.
  • Approve is named "Approve pairing request HX7K-29PQ" with aria-haspopup="dialog". The Dialog is modal, named by its title and described by its first line, or by the note when the request ran out. Station is a combobox described by the line under it. Row menus are named "Actions for Press cell 1". The note after the approval is role=status. At 320 the table regions are named "Pairing requests table, scrolls sideways" and "Stations table, scrolls sideways".

Focus after each action

  • The sign-in screen and Switch operator open with focus in Badge. An unknown badge keeps it there. A badge read with the PIN option on moves it to PIN.
  • After sign-in: the h1 of the job screen, "Press 4, Anna Berg". Cancel on Switch operator returns to the job screen with focus on Switch operator.
  • A plant in onboarding: the h1 "Plant D is not open yet". The pairing screen takes no input and has no focus target, also when a new code replaces one that ran out.
  • A wrong username or password: focus in the cleared Password. A wrong PIN: focus stays in the cleared PIN. PIN sign-in paused: focus stays in PIN.
  • Admin: Approve opens the Dialog with focus on Station. After Approve pairing the request row is gone, so focus moves to the station's link in the table; Cancel returns focus to Approve. When the request ran out, the Dialog keeps only Close, with focus on it; Close moves focus to the Pairing requests heading, since the request's row is gone.

Tab order

  • Sign-in (rule 12.1, nobody signed in): Skip to main content, More, Badge, Sign in with username.
  • PIN: Skip to main content, More, PIN, System keyboard (or Keypad), Sign in, Scan again. The toggle follows the field it serves, as on the report form (OF16), although the keypad column sits after the card; keypad keys stay out of the tab order. PIN paused: Skip to main content, More, PIN, Sign in with username, Scan again.
  • Sign in with username: Skip to main content, More, Username, Password, Show password, Sign in, Scan a badge instead.
  • Switch operator (an operator is signed in, the screen leaves Switch operator out of the top bar): Skip to main content, Sign out, More, Badge, Sign in with username, Cancel.
  • Pairing screen: Skip to main content, More; the code and the steps take no focus.
  • Admin Dialog: Station, Cancel, Approve pairing; Close alone when the request ran out. Focus stays inside the Dialog until it closes.
