Recommendation: A, pages

A is the shape plan 06 and ADR 0062 already describe. screenRoute, through masterDataRoutes for registers, gives the list, the detail and the create and edit forms their own routes, titles and h1, so focus after navigation, Back, copied links and the title pattern work with no new URL key and no ADR change, and EntityListPage, EntityDetailPage and EntityForm for registers, the command forms for articles, stay as documented. The table keeps the full width of main (about 974 px at 1280), long forms such as production orders and routings get a page, the reason field sits on the form, never behind a disclosure, ready for the day a contract makes it required, and at 320 px the only addition is the sticky article number. Its cost is context and steps: reading one article leaves the list, and a one-field fix takes the row menu, Edit, Save and Back to the list, which the URL state makes cheap but not free. Two parts of the other options are worth keeping: B's counts, which A shows in each filter menu and on the chips, and C's review step, but only for the commands plan 06 lists under 3.3.4 (saving a draft, breaking a lock, releasing an order), not for every save. C's split view could return later as an escape level 2 screen for a register that people read row by row.
