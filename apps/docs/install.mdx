---
title: Install NorthMES
description: Run NorthMES on one Linux host with Docker Compose, from a fresh host to the first sign-in.
---

NorthMES runs on one host as Docker Compose services. The release bundle holds everything the host needs: `compose.yaml`, `Caddyfile`, `backup.sh` and `northmes.env.example`.

| Service | What it does |
|---|---|
| `db` | Postgres 18, with its data in the `db-data` volume |
| `bootstrap` | Creates the database roles, then exits. A second run changes nothing |
| `migrate` | Applies the pending database migrations, then exits. `app` starts only after it succeeds |
| `app` | NorthMES itself: the API and the web app, reachable only inside the Compose network |
| `caddy` | Serves HTTPS on port 443, and redirects port 80 to it |
| `backup` | Every night, writes the database and the site's files to `./backups`. Starts only when `.env` turns it on |

## Before you start

You need:

- A Linux host with Docker Engine and the Compose plugin.
- Ports 80 and 443 free on the host.
- A host name that the browsers on the shop floor and in the office can reach, such as `northmes.plant.local`.

NorthMES runs its own Postgres in the `db` service by default. To use a Postgres 18 server you already run, read [Use your own Postgres](#use-your-own-postgres) before you start NorthMES for the first time.

## Install

<Steps>
  <Step title="Copy the bundle to the host">
    Download the bundle from the release page, unpack it on the host and go into its folder.
  </Step>
  <Step title="Create the settings file">
    ```sh
    cp northmes.env.example .env
    ```

    Edit `.env`:

    - `NORTHMES_VERSION`: paste the line from the release notes, for example `NORTHMES_VERSION=0.0.1@sha256:...`. The digest pins the exact image.
    - `NORTHMES_HOST`: the host name browsers use.
    - `NORTHMES_BIND_IP`: the address Caddy listens on. `0.0.0.0` opens ports 80 and 443 on every network interface of the host; if the host has more than one, set the address the plant network uses.
  </Step>
  <Step title="Create the secret files">
    Each file holds one random value. Only the user the NorthMES image runs as (uid 1000) can read them.

    ```sh
    umask 077
    mkdir -p secrets
    for name in postgres_password db_owner_password db_app_password db_auth_password auth_secret; do
      openssl rand -hex 32 > "secrets/$name"
    done
    sudo chown 1000:1000 secrets/*
    chmod 600 secrets/*
    mkdir backups
    ```

    Keep a copy of `secrets/` somewhere safe. Without it you cannot reach the database in the `db-data` volume.
  </Step>
  <Step title="Start NorthMES">
    ```sh
    docker compose up -d
    ```

    `bootstrap` and `migrate` run once and exit, then `app` and `caddy` start. `docker compose ps` shows the state of each service.
  </Step>
  <Step title="Create your company and its first admin">
    ```sh
    docker compose run --rm app company create --name "Your company" \
      --admin-username admin --admin-email admin@example.com --reason "first install"
    ```

    The command prints a temporary password once. Copy it now.
  </Step>
  <Step title="Sign in">
    Open `https://<NORTHMES_HOST>/sign-in` and sign in with the email and the temporary password. NorthMES then asks you to choose a new password.

    ![The NorthMES sign-in page](/images/install/sign-in.png)
  </Step>
</Steps>

## Verify a release

Each release after 0.0.1 carries two GitHub artifact attestations for its image: a build provenance attestation, which names the commit and the workflow run that built the image, and an SBOM attestation, which signs the CycloneDX SBOM of the image. Release 0.0.1 has none.

The workflow `.github/workflows/release.yml` signs both on a GitHub-hosted runner, with a certificate that GitHub Actions OIDC issues for that workflow on `refs/heads/main`. A valid attestation names this signer:

- Issuer: `https://token.actions.githubusercontent.com`
- Identity: `https://github.com/northMES/northmes/.github/workflows/release.yml@refs/heads/main`

The release page also holds the SBOM as `northmes-<version>-image.cdx.json`, and the two attestation bundles as `northmes-<version>-image.intoto.jsonl` and `northmes-<version>-image.cdx.json.intoto.jsonl`.

You need the GitHub CLI (`gh`) on a machine with internet, signed in with `gh auth login`; a host without internet needs `gh` but no sign-in, because it verifies the bundles you copy to it. The digest is the part after `@` in the `NORTHMES_VERSION` line of the release notes.

<Steps>
  <Step title="Check where the image was built">
    ```sh
    gh attestation verify oci://ghcr.io/northmes/northmes@<digest> \
      --repo northMES/northmes \
      --signer-workflow northMES/northmes/.github/workflows/release.yml@refs/heads/main \
      --deny-self-hosted-runners
    ```

    The command fails unless an attestation for exactly this digest was signed by the release workflow on `main`, on a GitHub-hosted runner.
  </Step>
  <Step title="Check the SBOM">
    ```sh
    gh attestation verify oci://ghcr.io/northmes/northmes@<digest> \
      --repo northMES/northmes \
      --signer-workflow northMES/northmes/.github/workflows/release.yml@refs/heads/main \
      --deny-self-hosted-runners \
      --predicate-type https://cyclonedx.org/bom
    ```

    To print the SBOM that the attestation signs, add `--format json --jq '.[0].verificationResult.statement.predicate'`.
  </Step>
</Steps>

### Verify on a host without internet

On a machine with internet, download the attestations for the digest and GitHub's trusted root, then copy both files to the host:

```sh
gh attestation download oci://ghcr.io/northmes/northmes@<digest> --repo northMES/northmes
gh attestation trusted-root > trusted_root.jsonl
```

`gh attestation download` writes one file, `sha256:<hex>.jsonl`, that holds both attestations. On the host, verify against those files:

```sh
gh attestation verify oci://<registry>/northmes/northmes@<digest> \
  --repo northMES/northmes \
  --signer-workflow northMES/northmes/.github/workflows/release.yml@refs/heads/main \
  --deny-self-hosted-runners \
  --bundle sha256:<hex>.jsonl \
  --custom-trusted-root trusted_root.jsonl
```

Add `--predicate-type https://cyclonedx.org/bom` to check the SBOM attestation. `gh` reads the image's digest from the registry in the image reference, so `<registry>` is a registry the host can reach that holds the image with the same digest, such as a registry inside the plant. The trusted root changes a few times a year, so download a new one with each release you bring in.

## Use your own Postgres

NorthMES can use a Postgres 18 server you already run, next to the other databases on it, in place of the `db` service. Set this up at install, before the first `docker compose up -d`.

<Steps>
  <Step title="Create the database and an admin role">
    On that server, create a database for NorthMES and an admin role that can create roles and owns the database. A managed service's admin role already has `CREATEROLE`.

    ```sql
    create role northmes_admin login createrole password '<the admin password>';
    create database northmes owner northmes_admin;
    ```

    NorthMES needs the `btree_gist` extension, which ships with Postgres. A managed service that keeps a list of allowed extensions must have `btree_gist` on it, such as the `azure.extensions` parameter of Azure Database for PostgreSQL.
  </Step>
  <Step title="Point NorthMES at the server">
    In `.env`, select `compose.external-db.yaml`, which keeps `db` from starting, and name the server, the database and the admin:

    ```sh
    COMPOSE_FILE=compose.yaml:compose.external-db.yaml
    NORTHMES_DATABASE_URL=postgres://pg.example.com:5432/northmes?sslmode=verify-full
    NORTHMES_DB_ADMIN_USER=northmes_admin
    ```

    `COMPOSE_FILE` replaces the files Compose picks by default, so a `compose.override.yaml` you add must be named in it too: `COMPOSE_FILE=compose.yaml:compose.external-db.yaml:compose.override.yaml`.

    Never put a user or a password in the URL, because NorthMES refuses a URL that holds one. Keep `sslmode=verify-full`: it encrypts the connection and checks the server's certificate against the public certificate authorities, so the server must offer TLS with a certificate from one of them. Release 0.0.1 cannot add a private certificate authority for the database connection. Connect directly, not through a pooler in transaction mode, because migrations hold a session lock.
  </Step>
  <Step title="Store the admin password">
    Put the admin's password in `secrets/postgres_password` instead of a random value. Create the other secret files as in [Install](#install).
  </Step>
</Steps>

`bootstrap` logs in as the admin and creates the roles NorthMES runs as: `nm_owner` for migrations, `nm_app` and `nm_auth` for the app, and `nm_ext`. Their passwords come from the files in `secrets/`. `bootstrap` runs on every `docker compose up -d` and changes nothing once the roles exist, so keep the admin's password in its file.

`migrate` creates the `btree_gist` extension as `nm_owner`, in a schema of its own named `northmes_extensions`, unless the database already has it. `btree_gist` is a trusted extension, so `nm_owner` needs no superuser for it.

<Note>
  Role names are shared by every database on a Postgres server, so one server holds one NorthMES installation.
</Note>

## Trust the certificate

The browser warns about the certificate on the first visit, because Caddy signed it with its own certificate authority. To remove the warning, copy Caddy's root certificate out of the container and add it to the trusted certificates of each computer that uses NorthMES:

```sh
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./northmes-root.crt
```

## API rate limits

The REST API under `/api/v1` can limit how many requests each integration token sends per minute. The limits are off by default. Set them in `.env`, then run `docker compose up -d`:

| Variable | Values | Default |
|---|---|---|
| `NORTHMES_API_RATE_LIMIT` | `on` or `off` | `off` |
| `NORTHMES_API_RATE_LIMIT_READS` | requests per minute per token to `GET` routes, a positive integer | `600` |
| `NORTHMES_API_RATE_LIMIT_WRITES` | requests per minute per token to `POST` routes, a positive integer | `60` |

Reads and writes count apart, and each token counts on its own, whatever address it calls from. The count lives in the database, so every `app` process shares it. A token over its limit gets HTTP 429 with the code `core.request.rate_limited` and a `Retry-After` header with the seconds to wait. `app` does not start with a value outside these rules, and its log names the variable.

## Back up

Your backups are yours to keep, as with any self-hosted app. NorthMES writes them on the host; copying them somewhere safe is up to you.

`northmes.env.example` turns the `backup` service on with `COMPOSE_PROFILES=backup`. Every night at 02:00 UTC it writes three files to `./backups` and deletes those older than 7 days: the database (`northmes-<time>.dump`), the database roles without their passwords (`northmes-<time>-roles.sql`), and `secrets/`, `.env`, `compose.override.yaml` and Caddy's data (`northmes-<time>-files.tar.gz`). Only the owner of the `backups` folder can read them, because they hold personal data and every secret of the installation.

To take a backup now:

```sh
docker compose run --rm backup now
```

What stays yours:

- Copy `./backups` off the host every day and encrypt that copy.
- Keep the copies as long as your plant needs; the host keeps 7 days.
- Restore a backup on another machine now and then, to know that it works.

With [your own Postgres](#use-your-own-postgres), your provider backs the database up: Azure Database for PostgreSQL, for example, keeps 7 to 35 days with point-in-time restore. Comment out `COMPOSE_PROFILES=backup` in `.env` and back up `secrets/`, `.env` and `compose.override.yaml` with the rest of the host. The bundle's `README.md` says how to keep a dump of your own as well.

## Restore

To restore onto a new host, or after losing the `db-data` volume:

<Steps>
  <Step title="Copy the bundle and the backups">
    Copy the bundle to the host as in [Install](#install), without creating `.env` or `secrets/`, and copy your backups into `backups/`.
  </Step>
  <Step title="Put back the files">
    Name the backup by the time in its file names:

    ```sh
    time=20261015T020000Z
    sudo tar -xzf "backups/northmes-$time-files.tar.gz" --exclude=data
    ```
  </Step>
  <Step title="Restore the database and Caddy's data">
    ```sh
    docker compose run --rm bootstrap
    docker compose run --rm backup restore "$time"
    ```
  </Step>
  <Step title="Start NorthMES">
    ```sh
    docker compose up -d
    ```
  </Step>
</Steps>

With your own Postgres, restore the server with your provider's tools instead, for example Azure's point-in-time restore, which creates a new server. Put the new server's host name in `NORTHMES_DATABASE_URL` in `.env` and run `docker compose up -d`.

## Upgrade

<Steps>
  <Step title="Read the release notes">
    They give the new `NORTHMES_VERSION` line, and say whether the release adds database migrations.
  </Step>
  <Step title="Take a backup">
    With the bundled database, run:

    ```sh
    docker compose run --rm backup now
    ```

    With your own Postgres, take your provider's on-demand backup, and back up `secrets/`, `.env` and `compose.override.yaml`.
  </Step>
  <Step title="Change the version">
    Put the new line in `.env` in place of the old one.
  </Step>
  <Step title="Restart on the new version">
    ```sh
    docker compose pull
    docker compose down
    docker compose up -d
    ```
  </Step>
</Steps>

`migrate` prints each migration it applies. If it fails, `app` does not start, and `docker compose logs migrate` shows why.

If you installed plugins, read [Before you upgrade NorthMES](/plugins#before-you-upgrade-northmes) first.

## Go back to the previous version

Put the previous `NORTHMES_VERSION` line back in `.env`, then run:

```sh
docker compose down
docker compose up -d
```

This works only while the newer release added no migration. The release notes say whether it did.

When it added one, going back means restoring the backup you took before the upgrade, which loses what was written since. Put the previous `NORTHMES_VERSION` line back in `.env`, then:

```sh
time=20261015T020000Z  # the backup you took before the upgrade
docker compose down
docker volume rm northmes_db-data
docker compose run --rm bootstrap
docker compose run --rm backup restore "$time"
docker compose up -d
```

## Files that stay yours

`.env`, `secrets/`, `backups/` and a `compose.override.yaml` you add are never part of a release. Copying a newer bundle over the folder keeps them.

## When something goes wrong

| What you see | Where to look |
|---|---|
| `app` does not start | `docker compose logs migrate`, then `docker compose logs app` |
| `app` keeps restarting, and its log reports it ran out of memory | Raise `NORTHMES_APP_MEM_LIMIT` in `.env` (2 GB by default, for example `NORTHMES_APP_MEM_LIMIT=4g`), then run `docker compose up -d` |
| The browser cannot connect | `docker compose ps caddy`, and that ports 80 and 443 are open on the host's firewall |
| A secret file error at start | The owner and mode of the files in `secrets/` (uid 1000, mode 600) |
